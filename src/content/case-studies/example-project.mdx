## Overview

This is an example case study that demonstrates the full content engine. Every heading, code block, callout, quote, and metric strip is rendered through the design system primitives.

The prose you are reading flows through our MDX component mapping — headings use `Heading`, paragraphs are styled with our type scale, and links use the accent color with proper underlines.

## The Problem

Building a content engine that renders consistently across case studies and articles requires careful coordination between the design system, MDX compilation, and content loading.

### Technical Challenges

The key challenges included:

- **Frontmatter validation** at build time using Zod schemas
- **Syntax highlighting** that works in both light and dark themes
- **Table of Contents** generation from heading structure
- **Reading time** calculation from word count

<Callout variant="insight" title="Key Decision">
  We chose to build custom MDX component overrides instead of using the Tailwind
  Typography plugin. This gives us full control over every rendered element.
</Callout>

## Architecture

The content engine follows a pipeline architecture:

1. MDX files are read from `src/content/`
2. Frontmatter is extracted and validated via Zod
3. Content is compiled by `@next/mdx` with rehype/remark plugins
4. Components are rendered through `mdx-components.tsx`
5. Pages are statically generated at build time

### Code Example

Here is an example of how the content loader works:

```typescript
export function getAllCaseStudies(): ContentEntry<CaseStudyFrontmatter>[] {
  return sortByDateWithFeatured(
    loadContentEntries('case-studies', caseStudyFrontmatterSchema),
  )
}
```

Inline code also works: the `ContentEntry<T>` type wraps frontmatter with slug, reading time, and TOC data.
